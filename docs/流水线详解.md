# 流水线详解

本文说明各阶段的数据流、校验规则与排错方式。快速上手请看根目录 `README.md`。

---

## 一、数据流总览

框架与小说分家：`tools/ assets/ docs/` 是框架（进 git），
一本小说的全部内容都在 `library/<work_id>/` 里（被 `.gitignore` 整体排除）。

```
library/<work_id>/source.txt      原稿
library/<work_id>/glossary.json   术语表（译名统一）
library/<work_id>/readings.json   读音表（专名读音强制）
   │
   │ init_work.py                按空行切分段落 → p00001…
   │                             识别「第N話」→ 章节 c0001…
   ▼
library/<work_id>/work.json       段落 + 章节 + 译文 + 注音（唯一权威数据）
library/index.json                作品索引
library/<work_id>/<书名>.html      阅读器（数据内嵌，双击即读）
   │
   │ make_chunks.py --target units / chunks_600
   ▼
library/<work_id>/chunks/         原料分块（init 生成，默认 80 段）
library/<work_id>/units/          工作单元（默认 100 段）—— 生产调度的最小单位
library/<work_id>/chunks_600/     交付分块（默认 600 段）—— 成品文件的分块边界
   │
   │ api_pipeline.py             翻译 + 注音（并发、重试、缓存）
   ▼
library/<work_id>/parts/unit_XXXX.jsonl          单元产物
   │
   │ verify_all_units.py         硬校验（不过不给合并）
   │ merge_parts_to_chunks.py
   ▼
library/<work_id>/output/chunk_600_XXXX.zh_ruby.jsonl    成品
   │
   │ merge_llm_outputs.py        写回 work.json 并重建阅读器
   ▼
library/<work_id>/<书名>.html     可阅读
```

**关键点**：`work.json` 在 init 时只有段落与章节骨架（译文为空），
由 `merge_llm_outputs.py` 在每次合并后回填。段落 `ja` 字段一旦生成就不再变动，
是所有校验的基准。

**换书库位置**：设 `SHIORI_LIBRARY` 环境变量即可把整个书库挪到别的盘或同步目录。

## 二、产物格式

### 单元产物 `parts/unit_XXXX.jsonl`

每行一个 JSON，字段固定四个：

```json
{"id":"p01234","zh":"中文译文","ja_ruby_html":"<ruby>漢字<rt>かんじ</rt></ruby>を含む原文","ruby_notes":""}
```

- 换行一律用 JSON 转义 `\n`，**不写 `<br>`**
- 行数、顺序必须与 `units/unit_XXXX.jsonl` 完全一致

### 成品 `output/chunk_600_XXXX.zh_ruby.jsonl`

同样的四字段格式，按 600 段一块，`id` 与 `chunks_600/` 的分块边界对齐。

---

## 三、校验规则（管道内强制）

每批产出立即做四项机械判定，**任一不达标即视为该行不合格**：

| # | 规则 | 目的 |
|---|---|---|
| 1 | 每行是合法 JSON | 防止截断/格式漂移 |
| 2 | 行数与 id 序列与输入完全一致 | 防止漏行、增行、串序 |
| 3 | `ja_ruby_html` 去掉 `<ruby>`/`<rt>` 后与原文 `ja` **逐字符相同** | 防止模型改写日文 |
| 4 | 每个汉字都被某对 `<ruby>` 覆盖 | 保证注音 100% |
| 5 | 读音表里的词，其读音必须出现在该段 ruby 中 | 防止人名读音随批次漂移 |

第 3 条的还原方式由**标注类型**决定（`schema.ANNOTATIONS`）：
`ruby` 剥标签、`none` 恒等，`insert`/`paren` 为预留。详见 [多语言与扩展](多语言与扩展.md)。

规则 3 的判定口径与 `merge_llm_outputs.py` 完全一致（两边都做 `<br>`→换行、
去 `<rt>`、去标签、反转义）。

> `々`（重复符号）不计入"必须注音"的汉字：它没有独立读音，
> 通常与前字一起注音（如 `人々`→ひとびと）。

## 四、重试与兜底（四级）

```
① 整批请求
     └─ 不合格行 ↓（只重发这些行，不是整批）
② 批级重试（默认 4 次，带具体纠正提示：漏了哪些汉字 / 原文哪里被改）
     └─ 仍不合格 ↓
③ 逐行单独重试（请求极小，成功率最高）
     └─ 仍不合格 ↓
④ 脚本兜底重建：把模型给出的 (汉字, 读音) 对按顺序套回**原文切片**
   → 结果与原文逐字一致（结构上不可能改写日文），缺口记入 ruby_notes
```

第 ④ 级保证流水线不会卡死，同时保证"绝不篡改原文"这条底线不被突破。

## 五、断点续跑

| 层级 | 机制 |
|---|---|
| 单元 | `parts/unit_XXXX.jsonl` 存在且行数正确 → 整个单元跳过 |
| 批次 | `library/<work_id>/cache/uXXXX_bN.jsonl` → 中断重启不重复消耗 token |
| 合并 | `merge_parts_to_chunks.py` 从「已有成品 + parts」累积合并，重复运行结果一致 |

重跑同一条命令即可继续；它不会重做已完成的部分。

## 六、常用操作

```powershell
# 查看进度（并列出待办单元编号）
py -3.11 tools\unit_progress.py --work-id my-novel --list-pending

# 只跑某几个单元
py -3.11 tools\api_pipeline.py --work-id my-novel --units 12-20

# 换模型重做某些单元：先删产物再跑
Remove-Item library\my-novel\parts\unit_0012.jsonl
Remove-Item library\my-novel\cache\u0012_*.jsonl
py -3.11 tools\api_pipeline.py --work-id my-novel --units 12

# 补注个别漏注音的汉字
py -3.11 tools\patch_missing_ruby.py --work-id my-novel

# 统一专名译法（规则写在 library/<work_id>/terms.json）
py -3.11 tools\unify_terms.py --work-id my-novel          # 预览
py -3.11 tools\unify_terms.py --work-id my-novel --apply  # 执行
# 执行后需要重新合并：merge_llm_outputs.py

# 核查原稿与作品数据是否漏段
py -3.11 tools\audit_source_and_ruby.py --work-id my-novel --source library\my-novel\source.txt
```

## 七、排错

| 现象 | 原因 / 处理 |
|---|---|
| `未找到工作单元` | 还没跑 `make_chunks.py`，或 `--work-id` 不一致 |
| `未找到 API 密钥` | 设 `DEEPSEEK_API_KEY`，或写 `config/credentials.yaml` |
| 某些单元反复不完整 | 跑 `unit_progress.py --list-pending` 看缺口；单独重跑该单元 |
| 注音覆盖率不足 100% | 跑 `patch_missing_ruby.py` |
| 人名读音前后不一致 | 跑 `harvest_readings.py` 看 `readings.conflicts.md`，把定稿写进 `readings.json` |
| 想换译文风格 | 改 `prompts/translate.md`，见 [提示词修改指南](提示词修改指南.md) |
| 同一专名译法不统一 | 配 `library/<work_id>/terms.json` 后跑 `unify_terms.py` |
| 打开的不是最新内容 | 阅读器文件名取自作品的 `reader_name`（如 `my-novel-双语.html`）；若你打开的仍是旧的 `reader.html`，说明看的是历史文件，重新合并会生成新文件名并清理旧入口 |
| 阅读器空白 | 先 `Ctrl+F5`。仍空白 → F12 看 Console；常见原因是 HTML 模板缺了 `reader.js` 引用的元素（新增控件时必须同步 `tools/reader_builder.py` 的模板） |
| 阅读器很卡 | 检查是否误改成一次性渲染全部段落；正确做法是按章渐进渲染（见 `assets/reader.js` 顶部注释） |

## 八、阅读器结构说明

`reader.html` 是**单文件**：CSS / JS / 数据全部内联。这样 `file://` 双击即可阅读，
不需要起服务器（`fetch` 本地 JSON 会被 CORS 拦截）。

### 为什么必须按章渲染

一部长篇可能有数万段，每段还带 ruby HTML（平均 200+ 字符）。
一次性 `innerHTML = 全部段落` 会产生上千万字符的 DOM 操作，浏览器直接卡死白屏。
阅读器因此采用：

- **按章渐进渲染**：初始只渲染前 3 章，滚动接近底部再追加 3 章
- **滚动窗口回收**：窗口超过 40 章就把远端章节移除，DOM 规模有界
- **跳转冻结自动加载**：目录/书签跳转期间暂停追加与回收，避免"一直滚且卡顿"

### 本地数据

| 键 | 内容 |
|---|---|
| `reader.work` | 上次阅读的作品 id |
| `reader.layout` / `reader.fontScale` / `reader.dark` | 阅读偏好 |
| `reader.progress.<work_id>` | 阅读进度：`{para_id, chapter_id, t}`（**段落锚点**，不是像素） |
| `reader.bookmarks.<work_id>` | 书签数组（含章节标题与片段，便于列表识别） |

进度用段落 id 而非 `scrollY`：DOM 是动态的，同一个 `scrollY` 在不同时刻指向不同内容；
段落 id 永久稳定，重新分章、换模型重译都不会失效。

书签与进度**只存本地浏览器**，不写回 `library/<work_id>/work.json`——这样重跑翻译/注音不会冲掉你的记录。

## 九、备选路线：用 agent 而不是 API 生产

若不想用 API，可用 `tools/unit_task_prompt.md` 作为 agent 任务规范，
让 agent 逐单元产出 `library/<work_id>/parts/unit_XXXX.jsonl`。
只要产物格式一致，后续的校验、合并、出阅读器流程完全相同。

> 该路线在数万段的规模下开销明显更大（每个 agent 都要重放系统提示与上下文），
> 适合小批量或需要人工介入的场合。
